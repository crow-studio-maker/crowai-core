# Model system

The registry discovers packages under `models/<mode>/<version>/`. A valid package contains `manifest.json` and `__init__.py`. The public ID is `<mode>/<manifest.id>`, for example `code/v1.0`.

The Core validates path names, manifest shape, contract version, minimum Core version, known capabilities, required callbacks, duplicate IDs, and optional SHA-256 file integrity values. Production treats the model root as read-only application input and does not require it to exist. Model packages must not write logs, databases, caches, or debug captures into their version directories; mutable package state is Core-owned under `instance/model_state/<mode>/<version>/` (or `CROWAI_MODEL_STATE_DIR`). Development reload can be enabled with `CROWAI_MODEL_DEVELOPMENT_RELOAD=true`; when a loaded package fingerprint changes, the registry first runs the old package's optional `shutdown()` callback with a bounded wait, then purges/imports the new module. If shutdown fails or times out, reload is blocked and the old module remains reachable rather than being orphaned.

Capabilities are declarations, not authorization. The Core decides whether web search, attachments, networking, or other services are available. A manifest never proves that a package is safe or authentic. Model package Python is a trusted local plugin boundary: importing it executes Python code, and manifest/path validation is not a sandbox or publisher-authentication mechanism.

The registry deliberately separates **installed** from **runnable**. `installed_models` are structurally valid packages. A lightweight package-local readiness check marks a package runnable only when its configured runtime/model (and projector where applicable) files are usable; this check does not start llama.cpp. The shared resolver accepts the configured `llama-server.exe` or its package-local extensionless sibling (and the reverse), never searches `PATH` or the project root, requires an executable runtime on POSIX, and rejects empty/non-GGUF model/projector placeholders. `models_available` means at least one runnable model, and `default_id()` selects only from runnable packages. An installed-but-unavailable package may remain visible for diagnostics but cannot serve a request. Public status distinguishes missing from invalid requirement categories without exposing local paths. When zero models are runnable, Core remains operational in degraded mode and never invents a default model.
